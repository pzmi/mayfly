# Running the real-Tart checks (`cargo xtask hw01`)

The checks of HW-01 confirm on real Tart, the real Keychain and launchd what mayfly's adapters
assume (ADR 0015 as amended 2026-11-11, HW-01X in `doc/tasks.md`). They run on your Mac, from a
terminal, in a checkout of the commit you want checked. Nothing is installed or left behind; you
send back one JSON report.

## Before the first run

1. **A Mac with Apple silicon**, macOS 15 or later, logged in at the console.
2. **Rust** through rustup (`https://rustup.rs`). The checkout's `rust-toolchain.toml` selects the
   toolchain by itself.
3. **Tart 2.41.1** exactly: `tart --version` must print `2.41.1` (the `tart-version` check
   fails otherwise, and every other result describes that other version).
4. **cargo-nextest** at the pinned version: `cargo xtask install-tools cargo-nextest`.
5. **Confirm the runner pin.** `tools/hw01/images.toml` pins runner `2.338.2` with one SHA-256
   per package (`linux-arm64`, `osx-arm64`), the shape the image store takes
   (`[images.runners."X.Y.Z"]`, plan §11). The checksums were computed by downloading each
   `actions-runner-<platform>-2.338.2.tar.gz` from github.com's release downloads over HTTPS and
   are not yet cross-checked against the published release notes: compare them with the
   checksums on the v2.338.2 release page before the first run. To check another version, rename
   the table and set both checksums from that release's notes; a value of `owner-fills-in`
   leaves the `install-runner` checks and the `ImageStore` contract `not_run`.
6. **Disk and network.** About 60 GB free for a plain run, about 150 GB with `--macos`. The run
   downloads the pinned Linux image (about 3 GB) and, with `--macos`, the macOS image (about
   25 GB); `tools/hw01/images.toml` lists every host it reaches.

## The commands

From the checkout's root:

```bash
cargo xtask hw01                      # the Linux image: Tart CLI facts, the contracts, the Keychain
cargo xtask hw01 --macos              # also the macOS image (--random-serial, the VM limit, macOS guest)
cargo xtask hw01 --service-mode --service-user <user>   # also the launchd check (see below)
cargo xtask hw01 --report ~/Desktop/hw01-report.json    # the report somewhere else
```

The flags combine. Without `--report` the report is `target/hw01-report.json` in the checkout.
The command refuses to start on anything but macOS.

## What it touches

- **A throwaway directory** in your temporary directory (`mayfly-hw01-<run id>-…`, mode `0700`;
  the temporary directory's real path is resolved once first, so macOS's `/var` →
  `/private/var` link never appears in it), holding its own `TART_HOME`. The run prints its path
  and its record's path when it starts. Every `tart` call names that home explicitly; the run never reads
  or writes `~/.tart` or a `TART_HOME` you have set, and stops if its home is replaced while it
  runs. Every VM it makes is named `hw01-<run id>-…` (and `mfb-contract`, the `VmProvider`
  contract's base) inside that home.
- **A disposable keychain** in that directory, added to your keychain search list for the run.
  The run changes the list only if it can read it and it holds your login keychain, and puts it
  back at the end only if it is still exactly what the run left (otherwise it tells you, and
  leaves it); then the keychain is deleted. One check locks that keychain and
  reads from it: if macOS shows a password dialog, press Cancel (the check records what `security`
  answered).
- **A loopback registry** on `127.0.0.1` for the run only, never reachable from the network.
- **With `--service-mode`**: one `sudo` prompt, a directory `/private/tmp/mayfly-hw01-<run
  id>-service.<random>` (made by `mktemp`) owned by the user you named, and a LaunchDaemon
  `dev.mayfly.hw01.<run id>` in `/Library/LaunchDaemons` that boots a copy of the Linux VM as
  that user without a GUI session. The user must already exist, must not be you, and should be
  dedicated to this; the run never creates or deletes a user, and refuses if the plist already
  exists. The plist is removed right after the check boots the VM out; the directory at the end.
- **Registry credentials.** The run sets no `TART_REGISTRY_*` variable and gives Tart an empty
  `HOME`, but Tart 2.41.1 always also asks Docker's credential configuration and your login
  keychain (`tart login`) for registry credentials, and cannot be told not to. If you saved
  credentials for `ghcr.io`, the pulls may use them; the images are public, so anonymous pulls
  work, and no credential ever reaches the report.
- **Nothing else.** `cargo` builds the checkout's test binaries into its own `target/`.

Everything the run makes is written to its record before it is made (the `--service-mode`
directory: as soon as `mktemp` names it). On a normal exit (success, a failed check, or one
Ctrl-C) it deletes exactly what the record names, a VM only after reading its MAC again right
before the delete; then it stops and deletes any VM a contract suite left in the run's own homes
(the record cannot name those; each is listed), and removes the directory. Anything it could not
delete is printed as `NOT deleted` with the command that removes it, and listed in the report.

**After a crash or a second Ctrl-C** (which quits at once), cleanup has not run, and these may
remain: the run directory with its VMs and images; a `tart run` process per VM that was running
(they keep their VMs alive); the test keychain in your search list; with `--service-mode`, the
`/private/tmp/mayfly-hw01-…` directory and, if the crash came before the boot-out, the
LaunchDaemon (it would start the VM again at boot). Run

```bash
cargo xtask hw01 --cleanup <the run directory printed at the start>
```

It replays that run's record (stopping each VM, which ends its `tart run`), deletes exactly what
the record names and what the run's own homes still hold, restores the search list if nobody
changed it since, and removes the directory; it prints what it could not delete, with the command
for each. It never kills a process by pid from an earlier run: a `tart run` that outlives its
VM's stop is listed for you to end. The cleanup, the home checks and the redaction are pinned by the tests in
`tools/xtask/src/hw01/` (`tests.rs`, `redact.rs`, `report.rs`), which run them against
`mayfly-fake-tart`.

## How long it takes

Roughly 45 to 90 minutes for a plain run on a recent Mac (an estimate until the first report), most of it the first build of the test
binaries, the image download and the `ImageStore` contract (each of its cases pulls the contract
image from the loopback registry into a fresh home). `--macos` adds the macOS download and about
30 minutes. The run prints each step on stderr as it goes.

## What to send back

The report file, and nothing else: attach `target/hw01-report.json` (or your `--report` path) to
the HW-01 issue or send it to the maintainers. It is versioned JSON: for each check `pass`,
`fail` with bounded evidence (exit codes, JSON shapes with values replaced by their types, the
wording that matters) or `not_run` with its reason, plus the macOS, Tart and toolchain versions
and the image digests. Before anything is written, the hostname, your user name, your home path,
the serial number, the hardware UUID, tokens and keychain contents are replaced or dropped, every
MAC is replaced by a stable placeholder per VM, and paths are relative to the run's directory
(`$RUN`); evidence that still fails that check makes its check `fail` and is dropped. Read the
file before you send it if you like: it is plain text.

## The checks

| Ids | What they confirm | For |
|:--|:--|:--|
| `tart-version` | `tart --version` prints `2.41.1` | TART-01 |
| `pull-by-digest`, `cache-layout` | a pull by digest, its listing name, the cache entry (directory or link, files, `manifest.json` as served, `cache/content/`) | DP-07, TART-01 |
| `clone-from-digest`, `get-keeps-change-times`, `clone-onto-existing` | a clone from the cached digest leaves the cache files' change times alone; `get` too; a clone onto a name exits 64 | DP-07, TART-01 |
| `list-get-json`, `get-running` | the `list` and `get` JSON shapes, `Memory` in MiB, `Disk` in whole GB or `null`, the listing order | TART-01 |
| `set-random-mac`, `set-memory`, `missing-vm-errors` | MAC read-back, `--memory` before a run, exit 2 "does not exist" | DEC-01, DP-04, TART-01 |
| `run-lock-holder`, `exec-guest`, `exec-interactive-redirected`, `stop-delete-semantics` | the run lock held by `tart run`'s pid, `tart exec` and its exit codes, `exec -i` with output in files, stop and delete answers | DEC-01, TART-01 |
| `vm-provider-contract` | VP-01..VP-10, VP-13..VP-15 and VP-17 (`cargo xtask test --only real-tart`) | DP-04, DP-07 |
| `launcher-verify`, `contract-image`, `contract-image-macos`, `install-runner-linux` | the test launcher (`tools/hw01/launcher`) in a booted image, the image pushed to the loopback registry, `install-runner` | DP-05, DP-07 |
| `clone-offline`, `no-auto-prune`, `pull-link-form`, `pull-refusals` | a cached clone reaches no registry, nothing pruned, the link Tart writes for another manifest and its deletion, disk v1 and out-of-order layers refused | DP-07, TART-01 |
| `IC-01`..`IC-14`, `public-manifest-fetch` | the `ImageStore` contract on real Tart; the manifest fetched by digest from the public registry | DP-07 |
| `security-*`, `secret-provider-contract` | ADR 0058's `security -w` facts and SP-01..SP-08 on the real Keychain | SEC-02 |
| `macos-*`, `hypervisor-limit` | with `--macos`: the macOS image, `--random-serial`, `install-runner` in a macOS guest, the VM limit's wording | DP-04, DP-07, TART-01 |
| `launchd-service-mode` | with `--service-mode`: Tart runs a VM under a LaunchDaemon of a dedicated user | DP-07 |

`IC-14` (a Linux base listed beside a macOS one) runs with `--macos` and both runner pins: the
run then also pushes the macOS image with the test launcher (`contract-image-macos`), and the
image store picks each base's runner pin by its guest OS. Without them it is `not_run`.
